# Results: phases 1, 2 and 4 on CPU

Machine: Intel Core i5-6300U laptop (2 cores, 4 threads, AVX2), Linux 6.17, Python 3.12.3,
pennylane 0.45.1, lightning 0.45.0, catalyst 0.15.0, jax 0.7.1, qulacs 0.6.14, rustc 1.99.1.
Every run used `sweeps/cpu.sh`: `--threads 2 --budget 10 --timeout 300`, batches 100, 1k,
10k, 100k. Exact versions and arguments are in each folder's `env.json`.

## Phase 2 target

The handoff's phase 2 bar: match default.qubit to 1e-12 and beat `jax-hand-cpu` at every qubit
count and batch size. On this machine, peregrin-cpu is faster than the fastest other backend
in **all 68 cells**, in f64 and f32. The smallest margin is 1.34x (generic, f32, n=2, B=10k);
at B=100k the margin is 2.1x to 15.7x. Every peregrin row passed the correctness check: worst
error 3.1e-15 in f64 and 6.1e-7 in f32 against default.qubit f64. The first call, including
building the program, took at most 0.15 s.

This is one laptop. The handoff's reference numbers come from a Xeon, which has not been
re-run. Whether these results hold there is still to be measured.

## Fairness notes

- **jax-hand was made faster before comparing.** The first sweep showed jax-hand-cpu losing
  to dq-jax-cpu on owner-mri n=2 at B=100k, because the template interpreter applied
  per-circuit gates as a batched (B,2,2) einsum. It now applies them elementwise. The change
  made it faster everywhere, including on the generic circuit, where it replaced the original
  specialized version (7 to 41% faster at every n). Examples at B=100k f64:
  - owner-mri n=2: 604k to 5.3M circuits/s
  - angle-trainable: 504k to 1.7M circuits/s

  The old rows are kept in the `20261104-2344-*` folders and the new ones are in `*-jaxhand2`.
  The comparison above uses the new, faster rows.
- **Threads.** peregrin used 2 threads (`OMP_NUM_THREADS=2`, one per physical core). XLA does
  not read that variable, so the JAX backends were free to use all 4 logical CPUs. If this
  biases anything, it biases against peregrin.
- **Same work.** jax-hand and peregrin run the same gate-list template from `circuits.py`, and
  `tests/test_circuits.py` checks it against each circuit's PennyLane body to 1e-12. Both load
  the state directly, so `--embed amplitude` changes only the QNode backends. In the
  owner-mri-amp rows, peregrin and jax-hand therefore do the same work as in the stateprep
  rows.
- **Timing boundary.** peregrin is timed through `peregrin.Circuit.execute`: numpy in, numpy out,
  output allocation included, the same boundary as every other backend.
- **f32.** peregrin f32 means f32 state and f32 trig. The f32 rows of the other backends
  follow the README's precision notes; Catalyst and qulacs always run in f64.

## Other findings from the sweep

- **qjit mostly beats plain lightning.qubit here.** On this laptop, lightning.qubit+qjit is
  1.2 to 5.4x faster than plain lightning.qubit in 66 of 68 cells. The two exceptions are
  generic n=8 at B=100k, where it is 0.88x (f64) and 0.91x (f32). This mostly reverses
  Finding 3 from the handoff, which was measured on the Xeon. Both stay far behind the batched simulators: at most 16k
  circuits/s, against hundreds of thousands to tens of millions.
- **The paper's data came from lightning.gpu.** The owner never got qrack to work. On this
  laptop the paper's 4 qubit circuit runs at 2.2k circuits/s on plain lightning.qubit, and
  peregrin runs it at 6.3M circuits/s at B=100k (f64).
- **The paper's code differs from its Fig. 2.** The 4 qubit code closes the CNOT chain into a
  ring with CNOT(3, 0), and the 2 qubit code has its own gate sequence. `owner-mri`
  benchmarks the code, since that is what produced the data.
- **qulacs** is the slowest backend: 100 to 700 circuits/s. It runs each circuit twice
  (Finding 2), and B=100k was skipped because it was projected to exceed the timeout.

## How peregrin gets there (CPU)

- **Tiles of 8 circuits.** The state is stored struct-of-arrays, one 8-lane row per
  amplitude, so every gate is a SIMD loop across circuits. AVX2 is chosen at runtime, so the
  wheel stays portable.
- **Free permutations.** Runs of CNOT and SWAP move no data: the program relabels which row
  holds which amplitude when it is built.
- **Real-state tracking.** While the state is known to be real (real amplitudes, then H, RY,
  CNOT), the imaginary half of the arithmetic is skipped.
- **Fusion.** Consecutive single-qubit gates on a wire become one 2x2 matrix. Matrices that
  depend only on shared weights are computed once per call.
- **Vectorized trig.** Per-circuit angles go through a branch-free sin/cos that runs across
  lanes, accurate to about 1 ulp, with a library fallback for |x| >= 1e5.

## peregrin as a PennyLane device (`peregrin.cpu`, harness label `peregrin-qnode`)

`peregrin-qnode` runs each circuit's PennyLane body in a broadcast QNode on
`qml.device("peregrin.cpu")` (measured when it was still registered as `"peregrin"`; same code), the same way the `default.qubit` backend is timed. Tape
construction, preprocessing, decomposition and result assembly are all inside the timed
region. Folders: `results/20261105-1037-*-qnode`. All 68 rows passed the correctness check
(worst f64 error 3.1e-15).

**Against the other PennyLane devices** (default.qubit, dq-jax-cpu, lightning.qubit with and
without qjit, qulacs), it is faster in **all 68 cells**. The smallest margin is 1.77x
(owner-mri f64 n=4, B=100), and at B=100k the margin is 5.3x to 73x. The paper's 4-qubit
circuit at B=100k runs at 1.9M circuits/s on this device, against 2.2k on plain lightning.qubit.

**Against the hand-written baselines**, which are not PennyLane devices, PennyLane's overhead
shows. A QNode call costs about 2 ms of fixed time on this laptop (building the tape, batch
checks, preprocessing), and default.qubit pays the same. So `peregrin-qnode` loses to
jax-hand-cpu below about B=10k. It wins 26 of 68 cells against jax-hand-cpu, mostly at
B=10k and above. For the fastest small-batch path, call `peregrin.Circuit` directly
(`peregrin-cpu` above), or send larger batches through the device.
