# Contributing to peregrin

Thanks for your interest. Bug reports, questions, benchmark results from other machines, and
pull requests are all welcome.

## Reporting bugs and asking questions

Open an issue at https://github.com/carsonwolff/pennylane-peregrin/issues. A bug report is
most useful when it includes:

- a minimal circuit that shows the problem;
- what `default.qubit` returns for the same circuit;
- your OS, CPU, and Python, PennyLane and peregrin versions. `python -c "import peregrin, pennylane; print(peregrin.__version__, pennylane.__version__)"` prints the last two.

A wrong result is treated as the most serious kind of bug.

## Building from source

You need Python 3.10 or newer and a Rust toolchain (https://rustup.rs, Rust 1.80 or newer).

```bash
python -m venv .venv && source .venv/bin/activate
pip install maturin pytest
cd crates/python && maturin develop --release && cd ../..
```

## Running the tests

```bash
cargo test -p peregrin-core --release   # Rust: golden outputs from default.qubit, unit tests
pytest crates/python/tests              # the PennyLane device against default.qubit
cargo fmt --all --check
cargo clippy --workspace --release --all-targets -- -D warnings
```

CI runs all of these on Linux, Windows and macOS for every pull request.

The correctness bar is to match `default.qubit` to 1e-12 in f64 and 1e-4 in f32. A change
that needs a looser tolerance has to say why.

The golden test files in `crates/core/tests/golden/` are generated by
`bench/tests/export_golden.py`. Run it from `bench/`, with the benchmark dependencies
installed, when adding gates or measurements.

## Running the benchmarks

Benchmarks are not run in CI, because shared runners are too noisy. To run them on your own
machine:

```bash
cd bench
pip install -r requirements.txt
sweeps/cpu.sh               # the full CPU sweep; results land in bench/results/
python compare.py results/<folders> --md
```

Results from CPUs we have not measured are especially welcome. Please open an issue with the
`results/` folders attached.

## Pull requests

- Open or find an issue first, so the change can be discussed before work starts. Reference
  it in the PR (for example `Closes #12`).
- Keep each PR to one topic. Small, clear commits are easier to review than one large one.
- Add or update tests for any behavior change.
- Add an entry under `[Unreleased]` in `CHANGELOG.md`.
- If AI tools helped with the change, say so in the PR description and update `AI_USAGE.md`.
- Code style is `rustfmt` (see `rustfmt.toml`) and clippy with no warnings. Python follows
  the style of the existing files.
